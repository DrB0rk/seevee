# Seevee repository development agent guide

Audience: coding/review/research agents implementing **Seevee itself** in this repository.

This file is not for agents creating a user's CV.

If you are operating inside an end-user Seevee workspace, use the workspace-agent bundle under `skills/seevee-workspace-agent/` or the workspace-specific instructions generated by `seevee init`.

## Required reading

For any non-trivial repository change:

1. `.dev/README.md`
2. `.dev/IMPLEMENTATION_STATUS.md`
3. `.dev/DEVELOPMENT.md`
4. `.dev/QUALITY_GATES.md`
5. `.dev/specs/SCHEMA_ARCHITECTURE.md`
6. the task-specific specification
7. latest relevant audit in `.dev/audits/`

Task-specific specifications:

- dashboard/editor behavior: `.dev/specs/DASHBOARD_EDITOR.md`
- dashboard visual system: `.dev/specs/DASHBOARD_VISUAL_DESIGN.md`
- template/runtime work: `.dev/specs/TEMPLATE_AUTHORING.md`
- CLI/install/runtime lifecycle: `.dev/specs/CLI_INSTALLER.md`
- workspace-agent runtime implementation: `.dev/specs/WORKSPACE_AGENT_RUNTIME_SPEC.md`
- overall roadmap: `.dev/specs/DEVELOPMENT_PLAN.md`

## Audience boundary

Do not use the following as repository contribution instructions:

- `skills/seevee-workspace-agent/SKILL.md`
- `skills/seevee-workspace-agent/references/*`
- `docs/workspace-agent/CV_GUIDANCE.md`

Those files are product payload/reference material for agents operating inside user workspaces.

A repository-development agent may inspect them only to implement or test the user-facing runtime contract.

## Repository state

This project is currently architecture-first.

Before claiming a feature works, check `.dev/IMPLEMENTATION_STATUS.md`.

A written spec does not mean the runtime exists.

## Architectural invariants

- Treat public schemas as APIs.
- Runtime schema source of truth should become Zod under `packages/schema`; committed JSON Schema files should then be generated artifacts.
- Each CV is a separate complete JSON resource under `cvs/`.
- CV content, provenance, comments, presentation state, template source, runtime state, and agent-run data are separate concerns.
- A presentation references one CV and one template/version.
- Stable semantic IDs are identity; array positions are not.
- Long-lived field references use stable node IDs plus relative JSON Pointer.
- Comments use resilient selector stacks and never depend only on page coordinates.
- CV layout/styling is user/agent controlled. Seevee does not impose a house style on CV templates.
- A4 portrait is a default new-presentation profile only.
- Page-count targets are optional preferences.
- CV/resume best-practice research is workspace-agent guidance, not a dashboard validation policy.
- The dashboard shell is fixed product UI.
- Preview and PDF export use the same selected physical page model.
- Source-template changes are validated/compiled before activation.
- Writes are revision checked; no silent last-write-wins behavior.
- `seevee init` must be non-interactive and return terminal control after healthy detached startup.
- End-user installation is via GitHub-hosted installer/release assets, not npm.
- Seevee remains agent-agnostic.

## Workspace-agent packaging rule

The repository-maintainer `.dev/AGENTS.md` must never be copied into an end-user workspace.

`seevee init` must instead generate/copy dedicated workspace instructions derived from:

- `skills/seevee-workspace-agent/`
- `docs/workspace-agent/`

When changing workspace-agent behavior, update its skill/reference bundle and validate/package that skill separately.

## Schema change discipline

Until `packages/schema` exists, bootstrap JSON Schemas under `schemas/v1/` are the implementation contract.

After Zod implementation lands:

1. update canonical Zod source;
2. update migration if needed;
3. regenerate JSON Schema artifacts;
4. update semantic validators;
5. update fixtures;
6. run schema/migration/reference-integrity tests;
7. update affected developer and workspace-agent docs;
8. verify older supported workspace fixtures.

Do not hand-edit generated artifacts once generation is authoritative.

## Completion discipline

A repository task is not complete while relevant failures remain in:

- schema parsing/reference resolution;
- semantic validation;
- migration tests;
- typecheck/lint/test;
- render diagnostics;
- platform lifecycle tests;
- installer/release verification;
- documentation links.

If a component is only specified but not implemented, say so explicitly.
